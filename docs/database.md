# PostgreSQL, дані та файлове сховище

> Цей документ описує архітектуру зберігання даних, налаштування бази даних, міграції та правила безпеки середовища. Для швидкого локального розгортання використовуйте **5 кроків у [README](../README.md)** (окремий проєкт `bordergroup-demo`, `.env.demo`, міграції та `demo_admin`). Інструкції для production-середовища наведені в [release.md](release.md).

## 1. Конфігурація Docker Compose та облікові записи

### Контейнер бази даних та томи (Volumes)
* **Образ і мережа:** сервіс `db` працює на базі **PostgreSQL 17.12-bookworm** на внутрішньому приватному порту `5432` (без публікації на хост) із перевіркою стану (`healthcheck`) через `pg_isready`.
* **Іменовані томи:** для збереження даних використовуються персистентні томи (типові назви для production: `bordergroup_postgres_data`, `bordergroup_order_documents`, `bordergroup_report_exports` — префікс визначається назвою Compose-проєкту).
* **Застереження:** не підключайте сторонні volumes і **ніколи не виконуйте `docker compose down -v`** у production-середовищі, щоб уникнути втрати даних.

### Розмежування змінних середовища (Least Privilege)
Контейнери отримують виключно ті параметри, які необхідні для їхньої роботи:
* **Контейнер `db`:** приймає `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` для початкової ініціалізації.
* **Контейнер `api`:** підключається до БД через окремий рядок `DATABASE_URL` (`postgresql+psycopg://<user>:<percent-encoded-password>@db:5432/<db>`), а також отримує прикладні налаштування (`APP_NAME`, `DEBUG`, `SQL_ECHO`, `JWT_SECRET_KEY`, `CORS_ORIGINS`, параметри Ollama та шляхи до файлових сховищ). **Адміністративний пароль `POSTGRES_PASSWORD` до API не передається.**

### Ролі БД та управління секретами
* **Production vs Demo:** у production використовуються окремі адміністративна та прикладна ролі БД із розмежованими правами на виконання міграцій. Демо-середовище використовує ізольованого `demo_user` у порожній БД для швидкого та відтворюваного запуску.
* **Поведінка ініціалізації:** зміна змінних `POSTGRES_*` у конфігурації не переініціалізує вже створений volume і не оновлює паролі існуючих користувачів БД.
* **Безпека конфігурації:** у Docker пріоритет мають змінні, передані через `environment` (підставляються з `.env` / `.env.demo`), хоча сам застосунок підтримує `DB_ENV=local|server`. Заборонено комітити файли із секретами або виводити повну конфігурацію командою `docker compose config` — для валідації синтаксису використовуйте `docker compose config --quiet`.

## 2. Міграції та рольова модель

* **Канонічний інструмент міграцій:** управління схемою БД відбувається виключно через кореневі `alembic.ini` та директорію `alembic/` (у контейнері: `alembic -c /app/alembic.ini upgrade head`). Заборонено змішувати її з історією `backend/alembic/` або примусово підміняти ревізії через `alembic stamp`.
* **Базові ролі системи:** ревізія `d2511200abcd` гарантує наявність актуальних ролей: `ADMIN`, `MAIN_KOORD`, `KOORD`, `VYK`, `KER`. Історична роль `ANAL` (скасований кабінет аналітика) збережена в схемі для цілісності архівних записів, проте вхід під нею та нові призначення заблоковані.
* **Ініціалізація демо-даних:** утиліта `bootstrap_demo` створює обліковий запис адміністратора виключно в цільовій демо-БД і перериває роботу, якщо в базі вже є користувачі. Для оновлення існуючого демо-стенду достатньо перезібрати контейнер `api` та виконати `upgrade head` — повторний запуск `bootstrap_demo` не потрібен.

## 3. Розподіл даних між БД та файловим сховищем

Система використовує гібридний підхід: структуровані дані та метадані зберігаються в PostgreSQL, а важкі бінарні файли й тексти аналізів — у приватних файлових томах.

| Тип даних | Місце зберігання | Примітки щодо доступу та життєвого циклу |
| :--- | :--- | :--- |
| Програми, заходи, подання, ролі, показники, журнал аудиту, метадані звітів | **PostgreSQL** (`postgres_data`) | Основне реляційне сховище системи. |
| Завантажені версії наказів | **Приватний volume** (`/app/storage/orders`) | Ізольоване файлове сховище документів. |
| JSON-снапшоти піврічних звітів | **Приватний volume** (`/app/storage/reports`) | Зрізи даних для формування звітності НАЗК. |
| Тексти висновків локального ШІ | **Приватний volume** (`/app/storage/reports/analyses`) | У БД зберігаються лише посилання та метадані. |
| Ваги локальної LLM-моделі | **Docker volume** (`ollama_data`) | Кеш моделі `qwen2.5:3b` для роботи без інтернету. |

### Правила доступу та зворотної сумісності
* **Захищена видача файлів:** усі документи та звіти віддаються виключно через авторизовані ендпоінти API після перевірки прав доступу (пряма роздача через `StaticFiles` не використовується).
* **Міграція висновків ШІ (Legacy):** для записів, створених до переходу на файлове зберігання, підтримується читання тексту безпосередньо з БД до завершення перевіреної міграції; усі нові висновки зберігаються у файлах.
* **Архівні звіти:** раніше сформовані записи `AnalyticsReport` (від вилученого кабінету аналітика) не видаляються автоматично і залишаються в системі як історичний архів.

## 4. Моніторинг стану, мережевий доступ та резервне копіювання

### Перевірка працездатності (Healthchecks)
* `GET /health` — повертає `{"status": "ok"}` (підтверджує життєздатність вебсервера API).
* `GET /db` — повертає `{"status": "connected", "database": "PostgreSQL", "result": 1}`. *Примітка: успішний Docker healthcheck самого контейнера БД не гарантує коректності `DATABASE_URL` на боці API, тому перевіряйте саме ендпоінт `/db`.*
* `GET /` — відкриває веб-інтерфейс сторінки входу.

### Мережева ізоляція та доступ
* За замовчуванням API слухає лише локальний інтерфейс хоста (`127.0.0.1:8001`), а порт PostgreSQL взагалі не виводиться на хост-машину.
* Для захищеного командного доступу до сервера використовується **Tailscale Serve** (локальний запуск демо-версії VPN не потребує).
* Якщо для адміністрування БД потрібен SSH-тунель, не покладайтеся на захардкоджену внутрішню IP-адресу Docker-контейнера без перевірки актуального стану мережі.

### Резервне копіювання (Backup & Restore)
* **Комплексність бекапу:** дамп бази даних PostgreSQL без файлових сховищ наказів і звітів є неповним. Резервне копіювання має виконуватися узгодженою парою: **SQL-дамп БД + архів директорій `/app/storage/*`**.
* **Перевірка відновлення:** цілісність бекапів необхідно регулярно тестувати шляхом розгортання в окремому ізольованому контурі.
