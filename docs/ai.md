# Використання ШІ

ChatGPT використовували для обговорення архітектури проєкту,
підготовки правил роботи з AI-агентами та планування налаштування GitHub.

Цей файл доповнюємо під час розробки. Для кожного нового випадку
зазначаємо інструмент, задачу та як команда перевірила результат.

## Фронтенд кабінетів (Claude, Anthropic)

- Задача: шаблони й скрипти кабінетів виконавця, координатора, керівника,
  аналітика та адміністратора під наявний API; заглушки там, де ендпоінтів
  ще немає (роль користувача, реєстр наказів, довідник підрозділів,
  розділи для неадміністраторів, рішення керівника, звіти аналітика).
- Доопрацювання за технічною документацією: перевірка номера наказу
  за реєстром `/api/orders`, додавання наказів координатором, підтвердні
  матеріали й перенесення строків у картці заходу, сигнали Risk Flags
  (вкладка адміністратора, позначки RF у координатора, зведення в
  керівника й аналітика).
- Перевірка: unittest (`tests/test_frontend_pages.py`), ручний прохід
  усіма кабінетами на локальній БД із синтетичними даними; детектор
  на наборі за I півріччя 2026 (зріз 06.07.2026) повертає 29 сигналів.

## Аналіз наказу локальною моделлю Ollama

- Координатор може передати PDF, DOCX або TXT до `POST /api/orders/{id}/analyze`.
  API перевіряє доступ до заходу, витягує текст і надсилає його до Ollama.
- Файл обробляється в пам'яті API й не зберігається. Підтримується до 15 МБ;
  скановані PDF без текстового шару потребують OCR і тут не аналізуються.
- Ollama запускається лише з Compose-профілем `ai`, без опублікованого порту
  на хості. На сервері після оновлення коду запустіть:

  ```sh
  docker compose --profile ai up -d ollama
  docker compose exec ollama ollama pull qwen2.5:3b
  docker compose --profile ai up -d --build api ollama
  ```

- API звертається до `http://ollama:11434` у внутрішній мережі Compose.
  Модель `qwen2.5:3b` завантажується окремо й зберігається у volume `ollama_data`.
  Висновок є допоміжним аналізом: координатор має перевірити його за оригіналом.

## Аналіз подання Executions

Координатор натискає «Проаналізувати наказ» у картці конкретного подання.
`POST /api/executions/{id}/analyze` перевіряє доступ до заходу й подання,
читає лише зафіксовану версію `submitted`, перевіряє її SHA-256 і розмір.
Довільний файл або номер наказу клієнт не передає. Відповідь містить ID
подання, версію і зафіксований хеш. Аналіз не змінює статус погодження.

Основне правило моделі: порівняти зміст заходу з описаним у документі
заходом; дати оцінку відповідності, навести цитати і вказати відсутні
докази. Доручення провести захід не доводить, що його виконано. Рішення
приймає координатор. Це системна інструкція під час запиту, а не
донавчання ваг моделі. Текст документа розглядається як недовірені дані.

Unit-тести використовують підміну відповіді моделі. E2E не запускає
Ollama; якість висновків справжньої моделі слід перевірити на сервері
окремими синтетичними документами після розгортання.

## CPU-сервер: час очікування та обсяг відповіді — #48

`OLLAMA_TIMEOUT_SECONDS` (типово 600 с, допустимо 30–3600) і
`OLLAMA_NUM_PREDICT` (типово 768, допустимо 1–4096) передаються з
серверного env-файлу через Compose. Модель `qwen2.5:3b` і контекст
8192 не змінені. Після редагування env контейнер API потрібно
перестворити через CD; простий restart не оновить його environment.

Журнал наявного сервера показав приблизно 3,6 вихідного токена/с
і скасування запиту на 180 с. Для схожого короткого документа
768 токенів означає приблизно 3,6 хвилини генерації плюс підготовка
запиту й завантаження моделі. Це оцінка, а не гарантія часу для
довгих документів або одночасних запитів. Збільшення timeout не
прискорює обчислення; менший num_predict обмежує довжину висновку.

Модель проситься відповідати стисло. Якщо Ollama повертає
`done_reason=length`, API додає `output_truncated=true`, а UI показує,
що висновок може бути неповним. Це окрема ознака від обрізання
тексту вхідного документа. Джерело: [Ollama Chat API](https://docs.ollama.com/api/chat)
та [визначення done_reason](https://github.com/ollama/ollama/blob/main/llm/server.go).
