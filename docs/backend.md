# Бекенд: архітектура, дані, правила

## Що вже працює

| Функція із завдання | Де |
|---|---|
| Паспорт програми, три розділи, зв'язок «захід → ризик → індикатор» | `/program`, `/measures`, `/risks` |
| Реєстр ризиків, рівень за методологією НАЗК, карта ризиків без рейтингування | `/risks` |
| Кабінет виконавця: внесення стану, результату, показника, підтвердних матеріалів | `/my`, `/measures/{id}` |
| Погодження координатором: погодити або повернути з коментарем | `/review` |
| Контроль строків, нагадування, внутрішнє перенесення строку | панель, `/measures/{id}` |
| Сигнали RF1–RF7 із поясненням, які дані до них привели | `/flags`, `/rules` |
| Звіт за півріччя у структурі Порталу доброчесності НАЗК, CSV, друк | `/report` |
| Журнал дій: хто, коли, яке поле, було → стало | `/journal` |
| Незмінність підтвердних матеріалів, SHA-256 | маршрутів зміни й видалення немає |
| Ролі: адміністратор, координатор, виконавець, керівник, аналітик | `app/auth.py` |
| API для інтеграції (читання) | `/api/v1/...`, опис — `/docs` |

Ще не зроблено: управлінські рекомендації з відповідальним і строком, аналітична записка, експорт у DOCX/XLSX,
графіки динаміки, ключ сервісу для API, CSRF-токени у формах.

## Будова

```

  main.py            точка входу, сесія бази на запит, обробка помилок
  config.py          налаштування зі змінних оточення
  models.py          таблиці (SQLAlchemy 2)
  importer.py        завантаження синтетичного набору організаторів
  auth.py            вхід і ролі
  services/rules.py  УСІ правила — чисті функції без бази, годинника й ШІ
  services/monitor.py   збирає стан програми за півріччя, застосовує правила
  services/workflow.py  внесення, подання, погодження, матеріали, строки
  services/journal.py   журнал дій
  routers/           сторінки (pages), дії (work), адміністрування (admin), API (api), вхід (auth)
```

Зовнішніх сервісів система не викликає: потрібні лише застосунок і PostgreSQL, тому її можна розгорнути
в закритому контурі (`docker compose up`).

## Дані

Ідентифікатори — як у наборі: `Z-01` (захід), `KR01` (ризик), `P01` (підрозділ), `U-001` (користувач), `E-001`
(матеріал). Імен у системі немає — лише роль, підрозділ і посада.

- **Захід** належить розділу, підрозділу, виконавцю і (для другого розділу) ризику. Строк за програмою не змінюється;
  перенесення — окремі внутрішні рішення.
- **Виконання** — один запис на захід і півріччя. Дві незалежні ознаки: *стан виконання* (заявляє виконавець)
  і *етап погодження* (не подано → на погодженні → погоджено / повернуто).
- **Ризик** має ймовірність, наслідки, індикатор стану з базовим і цільовим значенням та вимірювання за датами.
- **Журнал** лише доповнюється.

Звітний період і дата зрізу даних — налаштування (з набору: 2026-H1 і 06.07.2026); їх змінює координатор
або адміністратор.

## Правила

Усі висновки — у `services/rules.py`; однакові дані завжди дають однаковий результат. Повний перелік із
формулюваннями показує сторінка `/rules`.

- Стан для Порталу: «виконано» → Виконано; «частково» → Частково виконано; інакше — «Строк виконання заходу
  не настав», якщо строк — дата після кінця періоду, і «Не виконано» в решті випадків.
- Рівень ризику: бал = ймовірність × наслідки; 1–2 низький, 3–4 середній, 6–9 високий, 12–16 критичний.
- Сигнали RF1–RF7e: прострочення, брак підтверджень, формальне закриття (індикатор ризику пройшов менше 10 %
  шляху), опис повторює зміст заходу, показник не досягнуто, повторні порушення строків, якість даних.
- Сигнал — привід перевірити, а не висновок про порушення. Стан заходу він не змінює; рішення ухвалює координатор.

## Перевірка на наборі організаторів

`backend/tests/test_dataset.py` звіряє систему з ключем і еталоном набору:

- знайдено рівно 29 сигналів із 29 очікуваних (`kliuch/ochikuvani-sygnaly.csv`), зайвих немає;
- звіт для Порталу збігається з еталонним у всіх 50 рядках і всіх полях;
- рівні ризиків збігаються з набором.

Решта тестів: правила окремо (`test_rules.py`), повний цикл через HTTP і права доступу (`test_flow.py`),
одночасні рішення на PostgreSQL (`test_concurrency.py`).

## Обмеження

- Демонстраційний вхід (`DEMO_MODE=1`) — без пароля; для реальної роботи `DEMO_MODE=0` і паролі від адміністратора.
- Форми захищені лише cookie `SameSite=Lax`; CSRF-токенів ще немає.
- Файли матеріалів зберігаються на диску; вміст не перевіряється антивірусом.
- API лише для читання і з тією ж сесією, що й сторінки.
