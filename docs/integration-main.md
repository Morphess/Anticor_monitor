# Канонічна схема та сумісність релізу

Це технічна пам'ятка про поєднану модель даних; актуальні команди —
[release.md](release.md). Карта **зовнішніх** систем — [integration-map.md](integration-map.md).

Використовується тільки коренева історія Alembic:

| Ревізія | Призначення |
|---|---|
| e360c96d9546 | Попередній workflow програм |
| a20b6e9f1042 | Перехід до версій наказів і незалежних подань виконавців |
| b14e28a0c6f9 | Метадані й початкове збереження аналізів |
| c2501120abcd | Файлові метадані аналізів та історія оцінювання ризиків |
| d2511200abcd | Заповнення відсутніх активних ролей |

Для e360→a20 перехід вимагає порожніх orders/evidences/executions;
при наявних даних він відмовляє. Не обходьте це stamp: потрібен
узгоджений backfill. Наступні релізи не видаляють програми, користувачів
або подання. Коренева історія й backend/alembic — не взаємозамінні.

Після upgrade head CD окремо переносить legacy-текст аналізу у файл,
перевіряє його й лише потім очищує текстове поле. Старий API перед
перенесенням зупиняється. Історичні ANAL-користувачі не видаляються,
але роль не активна. Bootstrap не замінює міграції й не скидає паролі.

Production volumes зберігають ті самі назви в проєкті bordergroup:
order_documents → /app/storage/orders,
report_exports → /app/storage/reports. API має UID 10001.
CD зберігає дамп БД **і** файловий архів. Не використовуйте down -v.

Пройдено репетицію на заповненій синтетичній БД: старі бізнес-таблиці
збережені, старий висновок читається з файла. Після виправлення ролей
окремо перевірено чистий demo та створення користувачів усіх активних
ролей через API. Це не доводить міграцію будь-якої сторонньої схеми:
перед production потрібні перевірка поточної ревізії та резервні копії.
