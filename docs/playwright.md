# Playwright E2E — Issue #42

Перевірки запускаються в окремому Docker Compose-проєкті `bordergroup-e2e-42`. На хості потрібні Docker Compose та Bash/flock (Fedora й GitHub Actions Linux). Node і браузер встановлюються всередині runner-образу; локально їх встановлювати не потрібно.

```bash
bash scripts/test-e2e.sh
# Еквівалентно, якщо npm уже встановлений:
npm run test:e2e
```

Скрипт збирає образи, застосовує **backend/alembic.ini** до порожньої тестової БД, створює синтетичні дані, очікує готовності API та запускає Chromium. Наприкінці прибираються лише контейнери/volumes цього фіксованого E2E-проєкту. Повторний запуск починається з чистої БД. Запуски в одному checkout захищені flock.

Звіт знаходиться в `e2e-artifacts/playwright-report/index.html`. Для перегляду з Fedora можна виконати `python3 -m http.server 9323 --bind 127.0.0.1 --directory e2e-artifacts/playwright-report` і відкрити http://127.0.0.1:9323. За помилки `e2e-artifacts/test-results/` містить screenshot, trace ; compose.log зберігається в e2e-artifacts/. Ці каталоги не комітяться. У CI вони зберігаються на 7 днів. Токени в trace належать лише синтетичним користувачам.

## Ізоляція

- Немає опублікованих портів API або PostgreSQL і немає доступу до наявних volumes застосунку.
- Compose запускається з явним файлом і проєктом та `--env-file /dev/null`.
- Фікстура відмовляє, якщо env-прапорець, ім'я БД, користувач чи hostname не відповідають E2E-конфігурації, або БД уже має користувачів.
- Конфігурація Playwright дозволяє лише `http://api:8000` і вимагає E2E-прапорець. Довільний серверний baseURL не підтримується.
- Усі паролі, JWT-ключі, користувачі й документ у тестовому Compose синтетичні. `.env` та серверні дампи не копіюються в build context.
- Ollama не потрібна для поточного workflow й не запускається.

## Що перевіряється

1. Неправильний пароль: 401 та видиме повідомлення про помилку.
2. Адміністратор: вхід, завантаження користувачів і підрозділів.
3. MAIN_KOORD: вхід, власна програма та кількість запланованих заходів.
4. KOORD: вхід і видимість направленої програми.
5. VYK → KOORD → VYK: персонально призначений захід, подання точного payload до `/api/executions/submit`, зафіксована версія/хеш, відмова виконавцю в погодженні (403), перегляд PDF координатором, погодження, збережений результат після перезавантаження.

Підготовка програми, направлення, персонального призначення та версії наказу здійснюється Python-фікстурою через ORM і файлове сховище. Відповіді API в браузері не мокаються. Створення й направлення програми через форми UI залишаються наступним розширенням; поточні тести перевіряють видимість уже підготовленого workflow.

Playwright не доводить безпечність міграції основної БД. Для реального розгортання окремо потрібен погоджений перехід з серверної ревізії; запуск свіжої тестової схеми цього не замінює. Кореневий CI та CD у межах цієї задачі не змінюються.

## Залежності поточного backend

Гілка тестів включає окремий prerequisite-коміт із раніше перевіреними серверними виправленнями URL підрозділів та executor.js. Це зміни лише фронтенду; бізнес-логіка, серверна БД і CD не змінюються.

На вихідному `backend` 5d429ff відомі розбіжності executor.js з Execution API та зайві слеші запитів підрозділів. Якщо їх ще не інтегровано, тест подання має впасти, а не бути skip або замінений mock. /analyst має окрему відому проблему та не включений до цього початкового набору.

Офіційна документація: [Playwright CI](https://playwright.dev/docs/ci-intro), [Docker](https://playwright.dev/docs/docker).

## Локальна перевірка

2026-11-20: Chromium (повний браузер, `channel: chromium`) у Docker — **5 passed**. Повний workflow включає фактичний POST подання, 403 при спробі погодження виконавцем, відповідь з PDF, відкриття blob-вкладки, погодження координатором та нове завантаження кабінету виконавця. Headless-shell не використовується: він завантажує PDF замість перегляду.

На вихідному backend перевірки відтворили зайві перенаправлення підрозділів і збій завантаження виконавця. Після перенесення серверних hotfix сценарії пройшли без mocks або skip. Перевірки не покривають весь застосунок: `/analyst` та відсутній stylesheet `role-ux.css` залишаються окремими відомими проблемами.
