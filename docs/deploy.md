# Контрольоване розгортання

Початковий локальний запуск — [README](../README.md), серверний порядок
для оператора — [release.md](release.md). Цей файл описує `scripts/deploy.sh`.

Аргументи: абсолютний шлях до серверного env, каталог резервних копій,
повний SHA поточного checkout. Запуск — з кореня чистого worktree.
Сам скрипт перевіряє збіг HEAD та належність локально відомій origin/main,
але не робить fetch і не перевіряє CI. Через CD цим керують workflow та
[SSH-обробник](cd-ssh.md), які вимагають актуальну вершину main.

## Послідовність

1. Git-стан, SHA, відсутність сторонніх файлів у каталогах збірки та flock.
2. Compose config --quiet, health БД і авторизований SELECT 1.
3. Custom-format дамп БД, перевірка каталогу архіву, права 600.
4. Збереження тегу попереднього образу API та збірка нового.
5. Архів приватних orders/reports; перевірка адреси й назви БД застосунку.
6. Перегляд ревізій, upgrade head і current --check-heads кореневої історії.
7. Зупинка старого API, перевірене перенесення legacy-висновків у файли.
8. Перестворення API та повторні HTTP-перевірки /health і /db.

Перед запуском потрібні місце для дампа/архіву/образу, зелений CI,
погоджене вікно короткої недоступності та перевірка сумісності міграції.
Під час більшої частини міграцій старий API ще працює; схема має бути
сумісною з ним до зупинки. Поточний скрипт не гарантує довільних міграцій
без downtime. Оновлюється лише API, volumes БД і Ollama не видаляються.

Усі ручні та CD-запуски мають використовувати один каталог backup;
`deploy.sh` займає `.deploy.lock`, SSH-обробник — `.cd-gate.lock`.

## Помилка і відновлення

Скрипт зупиняється на помилці. API може залишитися зупиненим, якщо
помилка виникла при перенесенні висновків. Перевірте етап, стан БД,
файлів і контейнерів перед повторним запуском. Автоматичного rollback
немає: старий код може не підтримувати нову схему й файлові висновки.
Відновлювати тільки узгоджену пару БД+файлів із урахуванням змін після
backup. Тег rollback зберігає образ, але сам не відновлює дані.

Файли накопичуються: політика зберігання й вільне місце потрібні і для
БД, і для файлового сховища. HTTP 200 не доводить правильності всього
workflow; оператор окремо перевіряє вхід ролей, наказ, аналіз і звіт.
