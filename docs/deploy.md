# Контрольоване розгортання

Скрипт `scripts/deploy.sh` призначений для запуску з кореня worktree
на сервері. Він приймає:

1. Шлях до серверного `.env`.
2. Каталог резервних копій.
3. Повний SHA коміту для розгортання.

## Перед запуском

- Переконатися, що зміни пройшли PR, рев'ю та CI.
- Повідомити команду про можливу коротку недоступність API.
- Перевірити стан серверної БД і наявність місця для резервної копії.
- Оновити локальне посилання `origin/main` через `git fetch origin main`.
- Перевірити робочий каталог і вибрати потрібний коміт `main`.

Скрипт перевіряє, що SHA збігається з поточним HEAD і входить до
локально відомої історії `origin/main`. Сам скрипт не перевіряє CI
та не виконує `git fetch`.

## Послідовність скрипта

1. Перевірка Git-стану, SHA та блокування іншого запуску.
2. Перевірка Compose і доступності PostgreSQL.
3. Створення резервної копії та перевірка її каталогу.
4. Збереження тегу поточного образу API.
5. Збірка нового образу.
6. Звірка адреси та назви БД застосунку з БД резервної копії.
7. Перегляд і застосування міграцій Alembic.
8. Оновлення API та перевірка `/health` і `/db`.

Усі запуски на сервері мають використовувати той самий каталог
резервних копій: у ньому зберігається файл блокування `.deploy.lock`.

## Якщо сталася помилка

Скрипт зупиняється на команді, яка завершилася помилкою. Перевірте
вивід і стан API та БД перед повторним запуском.

Якщо помилка сталася після міграції, не застосовуйте автоматично
старий образ або відновлення БД: попередня версія API може бути
несумісна з новою схемою, а відновлення копії може видалити зміни,
зроблені після її створення. Узгодьте відновлення з командою.

Тег `bordergroup-api:rollback-...` зберігає попередній образ, а шлях
до резервної копії виводиться під час розгортання. Автоматичний
rollback не реалізовано.

## Обмеження поточної версії

- Немає автоматичної перевірки результату CI.
- Скрипт зупиняється, якщо в каталогах коду, ресурсів фронтенду
  та міграцій є неіндексовані або ігноровані Git файли. Перед
  повторним запуском їх потрібно переглянути.
- Під час міграції стара версія API залишається запущеною; зміни
  схеми потрібно перевірити на сумісність із нею.
- `/health` і `/db` перевіряються за HTTP-статусом; повний
  користувацький сценарій потребує окремої перевірки.
- Перевірка DATABASE_URL допускає PostgreSQL на хості `db`, порт
  `5432` і не допускає додаткових query-параметрів.
