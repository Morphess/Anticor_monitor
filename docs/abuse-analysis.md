# Можливі зловживання та запобіжники

Це аналіз загроз MVP на синтетичних даних. «Є» означає механізм у коді,
а не гарантію захисту від усіх атак. Технічні перевірки й їх межі описані
в [security-review.md](security-review.md).

| Сценарій | Наслідок | Запобіжник, який є | Залишковий ризик / розвиток |
|---|---|---|---|
| Формально закрити захід, щоб покращити KPI | Статистика приховає невиконання | Подання окремо від погодження; RF для показників, описів і підтверджень; видимі неповні дані | Координатор може погодити неправдивий зміст; потрібен вибірковий незалежний контроль |
| Додати наказ, який лише доручає провести захід | Намір видається за результат | Версія документа, перегляд координатором, правило підказки ШІ відрізняє доручення від виконання | ШІ може помилятися; людина перевіряє факти, дати й результати |
| Замінити файл або номер після подання | Погодження стосується іншого доказу | Зафіксовані версія/SHA-256; перевірка цілісності, guard погодження й історія заміни номера | Адміністратор хоста може змінити і БД, і файли; потрібен зовнішній незмінний архів |
| Читати чужі заходи чи документи | Витік даних іншого підрозділу | Серверні перевірки ролі, власника, призначення та дерева підрозділів; негативні API/E2E тести | Помилкове призначення адміністратором дає легальний доступ; потрібен перегляд прав |
| Підкинути наказ без входу | Фальшивий реєстровий доказ | Реєстр вимагає ADMIN; Execution API авторизує подання | Компрометація ADMIN залишається ризиком; MFA/SSO не реалізовані |
| Багаторазово переносити строки | Приховати прострочення | Журнал перенесень, RF6 та перевірка первинного строку | Сигнал сам не забороняє всі переносення; потрібен управлінський розгляд |
| Занизити оцінку ризику | Зробити проблему непомітною | P/I обмежені 1–4; score=P×I; журнал переоцінювання й захист завершених записів тригером | Вхідні оцінки можуть бути упереджені; потрібні докази та незалежний перегляд |
| Інструкція у документі для моделі (prompt injection) | Хибна підказка або приховування прогалин | Документ оголошений недовіреним; модель не має інструментів погодження чи виконання команд | Prompt не гарантує імунітету; висновок перевіряє людина |
| XSS або формула у звіті | Виконання коду в браузері чи таблиці | textContent/escaping у UI і HTML; небезпечні CSV-префікси екрануються | Не є повним аудитом усіх браузерів і редакторів; потрібне розширення тестів |
| Засипати сервер ШІ-запитами | Виснаження CPU/RAM, недоступність API | Ліміт файла/тексту/сторінок, timeout, ліміт токенів, кеш; блокування одного подання | Загальної черги та rate limiting немає; різні подання можуть навантажити сервер |
| Видалити або змінити звіт | Втрата історії чи неправильне рішення | Приватні файли, SHA-256 для ШІ, авторизоване читання, БД+файлова резервна копія в CD | Немає WORM або зовнішнього підпису всіх звітів; резервні копії потребують тесту відновлення |
| Використати реальні службові дані в публічному MVP | Розкриття інформації | Інструкції про синтетичні дані, ignore/context-правила, перевірка типових секретів | Немає автоматичного DLP; команда перевіряє історію й усі публічні артефакти |

## Принципи управління

Сигнал не є доказом корупції й не повинен автоматично карати працівника.
Не оцінювати людей лише за кількістю «закритих» заходів: окремо дивитися
на стан ризиків, показники, підтвердження, пояснення та рольові межі даних.
Не порівнювати підрозділи без урахування складності завдань і повноти даних.

До виробничого використання потрібні погоджені строки зберігання,
періодичний перегляд доступу, незалежний аудит і перевірка відновлення.
Якщо ШІ недоступна, координатор перевіряє документ сам; модель не є
обов'язковим шлюзом до погодження чи формування звіту.

## Приклад перевірки змісту

У [синтетичному звіті](examples/README.md) один прострочений захід без
подання не став «виконаним». Звіт містить невиконання й відсутнє пояснення;
управлінська рекомендація називає строк і пропонує перевірити затримку.
Приклад показує лише цей сценарій, а не доводить захист від усіх загроз.
